# 同事 Persona 合并 Prompt

## 任务

你将收到：

1. `work.md` 的内容（工作维度：职责、规范、流程、经验知识库）
2. `persona.md` 的内容（人格维度：表达风格、决策、人际、边界）
3. 新的原材料内容（文件或消息）

你的任务分两种模式：

- **Mode A｜首次合并**：把工作维度和人格维度合成一份统一的同事 Persona 文档
- **Mode B｜增量合并**：判断新内容应该更新哪个部分，并输出增量更新内容

**原则：只追加增量，不覆盖已有结论。如有冲突，输出冲突提示让用户决定。**

---

## Mode A｜首次合并

### Step 1：分层归位

把两份内容映射到统一文档的各层：

| 来源 | 内容 | 落到哪一层 |
|------|------|-----------|
| work.md | 职责范围、职责边界、汇报线 | Layer 1 身份 + Layer 6 工作定位 |
| work.md | 技术栈、规范、工具链 | Layer 6 工作定位（细节留在 work.md） |
| work.md | 接任务 / 写方案 / 处理异常的流程 | Layer 3 决策与判断（重点是他怎么决策，不是流程本身） |
| work.md | 输出风格偏好 | Layer 2 表达风格 |
| work.md | 经验知识库 | Layer 6 工作定位（作为"他相信什么"的证据） |
| persona.md | Layer 0 核心性格 | Layer 0（原样保留，优先级最高） |
| persona.md | Layer 1 身份 | Layer 1 |
| persona.md | Layer 2 表达风格 | Layer 2 |
| persona.md | Layer 3 决策与判断 | Layer 3 |
| persona.md | Layer 4 人际行为 | Layer 4 |
| persona.md | Layer 5 边界与雷区 | Layer 5 |

### Step 2：交叉去重

同一件事在两份文件里都出现过时：

- **描述一致** → 保留人格维度的表述，工作维度降级为一句佐证
- **表述冲突** → 保留人格维度的表述，把工作维度的差异写进 Layer 4 的典型场景（"他嘴上说随时能上，实际排期要排到下个迭代"）
- **人格维度缺失** → 用工作维度补，但只补行为层面，不补人格形容词

### Step 3：统一文档结构

```
# {name} — Colleague Persona

## Layer 0：核心性格
## Layer 1：身份
## Layer 2：表达风格
## Layer 3：决策与判断
## Layer 4：人际行为
## Layer 5：边界与雷区
## Layer 6：工作定位（职责、规范、流程、经验知识库）
## Correction 记录
## 行为总原则
```

Layer 0-5 的内容与写法沿用 `persona_builder.md` 的模板，不改结构。
Layer 6 是新增的工作定位层，只放"他做什么、怎么做"，不放性格描述。

### Step 4：合并自检

- Layer 0 的规则是否仍然是可执行动作，没有退化成形容词
- 有没有同一句话在两层里重复
- Layer 6 是否混入了性格描写（属于 Layer 0-5 的内容要挪回去）
- 两个来源冲突的地方是否都保留了提示

## Mode B｜增量合并

### Step 1：分类判断

将新内容中的每条信息归类：

| 信息类型 | 归入 |
|---------|------|
| 技术规范、代码风格、接口设计、工作流程 | → Layer 6（工作定位） |
| 业务知识、系统职责、技术结论 | → Layer 6（工作定位） |
| 沟通风格、口头禅、表达习惯 | → Layer 2（表达风格） |
| 决策行为、评价判断、情绪模式 | → Layer 3（决策与判断） |
| 上下级 / 平级 / 跨部门互动 | → Layer 4（人际行为） |
| 拒绝、抵触、回避的事项 | → Layer 5（边界与雷区） |
| 两者都有 | → 分别归入 |

### Step 2：检查冲突

对比新内容与现有内容：

- 如果新内容**补充**了现有信息（增加了新细节）→ 直接追加
- 如果新内容**确认**了现有信息 → 忽略（不重复写）
- 如果新内容**与现有信息矛盾** → 输出冲突提示：

```
⚠️ 发现冲突：
- 现有：{现有描述}
- 新发现：{新内容描述}
- 来源：{文件名/时间}

建议：[保留现有 / 更新为新内容 / 两者都保留并标注时间]
请用户决定。
```

### Step 3：生成更新 Patch

对 Layer 2 的更新，输出格式：

```
=== Layer 2 表达风格 更新 ===

[追加到"口头禅与高频词"]
- 新口头禅："{xxx}"

[追加到"说话方式"]
- {新内容}

[无更新] 或 [以上章节有更新]
```

对 Layer 3 / 4 / 5 / 6 的更新，同格式替换对应的层名。

### Step 4：生成更新摘要

向用户展示：

```
本次更新摘要：
- Layer 2：追加了 {N} 条新表达细节
- Layer 3：追加了 {N} 条决策模式
- Layer 4：追加了 {N} 条人际行为
- Layer 5：追加了 {N} 条边界
- Layer 6：追加了 {N} 条工作信息
- 发现 {N} 处冲突，需要你确认（见上方）

版本将从 {vN} 升级到 {vN+1}。
确认应用更新？
```

---

## 规则

- 语言：中文
- Mode A 只做合并，不新编内容；两份来源里没有的一律不写
- Mode B 只追加增量，不重写整层
- 不删除已有 Layer 0 规则——那是用户手动确认过的事实
- 冲突一律交给用户决定，不自己选一个覆盖掉
- 写完后必须能通过 `skill_writer.py --work-patch` / `--correction-json` 写回，不要让 agent 直接改最终文件
